# Инструкция для ИИ-агента: работа со STALCRAFT API (EXBO)

Этот документ — рабочая инструкция для агента, который получает данные игры STALCRAFT через публичный HTTP API EXBO. Следуй ей как набору правил: что можно, что нельзя, как не попасть в типовые ловушки.

> **Статус API:** официально бета. Эндпоинты могут меняться без объявления.
> **Главное правило разбора ответов:** неизвестное поле, неизвестный тип блока и неизвестный id не должны ронять обработку.
> **Источник правды по ограничениям:** ограничения нигде официально не опубликованы. Числа ниже — замеры сообщества (даты указаны). Если твой замер расходится — верь замеру.

**Источники и их приоритет.** Документ собран из двух слоёв; помечай для себя, что откуда:

- **Официальная документация EXBO** — `https://eapi.stalcraft.net/` (разделы: [Overview](https://eapi.stalcraft.net/overview.html), [Application Management](https://eapi.stalcraft.net/registration.html), [Authentication](https://eapi.stalcraft.net/auth.html), [Items Database](https://eapi.stalcraft.net/items.html), [Terms of Use](https://eapi.stalcraft.net/terms.html), [API Reference](https://eapi.stalcraft.net/reference)). Это источник по схеме авторизации, структуре базы предметов и условиям использования.
- **Практические наблюдения** (замеры Lunar и др.) — всё про реальное поведение: лимиты, устаревший срез, расхождения демо и боя, особенности полей. Помечено «замер» / датой.
- **Каноническая схема эндпоинтов** — интерактивный [API Reference](https://eapi.stalcraft.net/reference) (рендерится JavaScript'ом, обычным HTTP-запросом страница приходит пустой). Раздел 5 ниже составлен по практике; **если схема из Reference или реальный ответ расходятся с разделом 5 — верь Reference и реальному ответу.**
- Если официальная документация и наблюдения противоречат друг другу, прямо сообщай об этом пользователю, а не выбирай молча (известные расхождения помечены в тексте).

## 1. Что API умеет и чего не умеет

| Умеет (только чтение, все запросы — `GET`) | Не умеет |
|---|---|
| Активные лоты аукциона и история сделок (по конкретному предмету) | Выставлять, покупать, снимать лоты |
| Публичный профиль персонажа по нику | Читать инвентарь, склад, деньги игрока |
| Список кланов и карточка клана | Данные PvP-матчей и статистику боёв |
| Состав клана (только с токеном участника этого клана) | Сообщать время **следующего** выброса |
| Статус выброса и время предыдущего | Искать предметы по названию (только по `id`) |
| Сессии операций с составом и статистикой | Мгновенные данные (аукцион отстаёт ~10 минут) |

Тела запросов нет ни у одного эндпоинта. Записать что-либо в игру через API нельзя.

## 2. Адреса и окружения

| Окружение | Адрес | Доступ |
|---|---|---|
| Основной (реальные данные) | `https://eapi.stalcraft.net` | Нужно одобренное приложение |
| Демо (заглушки) | `https://dapi.stalcraft.net` | Открыт всем, ключи публичные |

- **Домены.** Официальная документация сейчас пишет адреса на домене `stalzone.com` (`eapi.stalzone.com`, `dapi.stalzone.com`); в практике и старых материалах встречается `stalcraft.net`. Это один и тот же сервис (переименование игры), оба домена ведут в одно место. По наблюдениям (08.08.2026) отвечает `stalcraft.net`; если один домен не резолвится или отдаёт неожиданный ответ — попробуй второй. В примерах ниже используется `stalcraft.net`.
- То же с репозиторием базы предметов: в официальной доке он назван `stalzone-database`, фактический адрес — `stalcraft-database` (старый отвечает `301`, см. раздел 8).
- Пока приложение не одобрено, основной сервер отвечает `401` на всё (кроме `/regions`).
- Демо-сервер отдаёт 3–4 записи-заглушки на **любой** запрос и **игнорирует регион** (`/XX/clans` вернёт `200`). Обработку неизвестного региона на демо проверить нельзя.

**Публичные демо-ключи** (опубликованы самой EXBO, секретом не являются):

```bash
curl -X GET 'https://dapi.stalcraft.net/EU/clans?limit=3' \
  -H 'Client-Id: 1' \
  -H 'Client-Secret: E98cm6J9NNjTQopph0c2eIXNKafg4R1Cjz0TZh2D'
```

Используй демо, чтобы отладить разбор ответов до получения доступа. Если «на демо работает, на основном пусто» — почти всегда дело в регионе.

**Демо-токены (официально).** На странице [Overview → Demo API](https://eapi.stalcraft.net/overview.html#demo-api) EXBO публикует два готовых JWT-токена для демо-сервера: **App Access Token** и **User Access Token** (оба с `aud: "1"`, срок действия ~100 лет; пользовательский — с `sub: "1"`). Пользовательский демо-токен — единственный способ проверить на демо эндпоинты, требующие токен пользователя (например, `GET /EU/characters`):

```bash
curl -X GET 'https://dapi.stalcraft.net/EU/characters' \
  -H 'Authorization: Bearer <DEMO_USER_ACCESS_TOKEN>' \
  -H 'User-Agent: my-app/1.0'
```

Значения токенов бери со страницы Overview (они длинные, здесь не дублируются, чтобы не внести опечатку). Демо-токены публичны и ничего не защищают; на основном сервере они не работают. В ответе демо — три тестовых персонажа (`Test-1`, `Test-2`, `Test-3`) с кланами `Clan #1` / `Clan #2` и рангами `LEADER` / `OFFICER`.

## 3. Регионы

Список отдаёт `GET /regions` (единственный эндпоинт без токена; удобен как проверка связи).

| id | Название (основной) | Реалм | Есть в демо |
|---|---|---|---|
| `RU` | RUSSIA | ru | да |
| `EU` | EUROPE | global | да |
| `NA` | NORTH AMERICA | global | да |
| `SEA` | SOUTHEAST ASIA | global | да |
| `NEA` | NORTHEAST ASIA | global | **нет** |

Правила:

- **Сопоставляй регионы по `id`, а не по `name`.** У SEA название на демо — `SOUTH EAST ASIA`, на основном — `SOUTHEAST ASIA`.
- Не валидируй регион по демо-списку: NEA там отсутствует.
- Регион в пути регистронезависим (`/RU/`, `/ru/`, `/Ru/` равнозначны).
- Неизвестный регион на основном сервере → `400` `{"title": "Unknown region: XX", "status": 400}`.
- **Реалм** (`ru` / `global`) важен только для базы предметов (см. раздел 8).

### Идентификаторы

| Что | Вид | Правила |
|---|---|---|
| `id` предмета | короткая строка (`y1q9`, `0n9q`) | **Регистрозависим** (`0N9q` ≠ `0n9q`). Считай непрозрачной строкой. Один и тот же id в разных реалмах — один и тот же предмет |
| `id` клана | UUID | Постоянный, переживает переименование и смену тега |
| Ник персонажа | строка | В пути регистронезависим (единственное исключение). Кириллицу URL-кодируй |
| `id` сессии операции | 19-значное число | Не помещается в `Number` JS — см. раздел 7 |

## 4. Аутентификация

### 4.1. Получение доступа

1. Нужна учётная запись EXBO (при игре через Steam она создаётся автоматически).
2. Заявка подаётся **только** через телеграм-бота `@stalzone_api_bot`: команда `/newapp` (анкета, ручная проверка), `/myapps` (список приложений, redirect URI).
3. Описание приложения должно соответствовать реальному поведению — по нему заявку одобряют.
4. После проверки подтверждение приходит сообщением **в тот же чат** бота. Заявка — ручная, сроки не опубликованы; разрабатывай на демо параллельно. Доступ официально в раннем доступе (early access/beta) и выдаётся по запросу.
5. На выходе: `client_id` (публичный) и `client_secret` (**секрет**).

### 4.2. Правила обращения с секретами (обязательно)

- `client_secret`, `access_token`, `refresh_token` — приравнены к паролям.
- Хранить **только на сервере**, в переменных окружения / защищённом хранилище.
- **Никогда**: в браузерном JS, в расширениях, в мобильных приложениях, в репозитории, в логах, в ответах пользователю.
- В коде и примерах используй плейсхолдеры: `process.env.STALCRAFT_CLIENT_ID`, `process.env.STALCRAFT_CLIENT_SECRET`.
- Никогда не печатай секрет и токены в выводе, даже частично.

### 4.3. Какой токен выбрать

| Способ | Когда | Как |
|---|---|---|
| **Заголовки `Client-Id` / `Client-Secret`** (по умолчанию, ~90% задач) | Аукцион, кланы, профили, выбросы, операции | Два заголовка в каждом запросе, состояния нет |
| `client_credentials` | То же, но «по канону OAuth» | `POST https://exbo.net/oauth/token`, далее `Authorization: Bearer` |
| **Токен пользователя** | Персонажи игрока, состав клана, друзья | Полный цикл OAuth с входом игрока |

Токен пользователя принимается везде, где принимается токен приложения — обратное неверно.

**Способ 1 — заголовки:**

```bash
curl -X GET 'https://eapi.stalcraft.net/RU/emission' \
  -H 'Client-Id: <CLIENT_ID>' \
  -H 'Client-Secret: <CLIENT_SECRET>' \
  -H 'User-Agent: my-app/1.0'
```

**Способ 2 — `client_credentials`:**

```bash
curl -X POST 'https://exbo.net/oauth/token' \
  -d 'client_id=<CLIENT_ID>' \
  -d 'client_secret=<CLIENT_SECRET>' \
  -d 'grant_type=client_credentials' \
  -d 'scope='
```

Параметр `scope` обязателен, но **должен быть пустым**. Непустое значение — самая частая причина отказа. Ответ: `token_type`, `expires_in` (~год), `access_token` (JWT).

### 4.4. Токен пользователя (OAuth authorization_code)

Нужен для эндпоинтов `/{region}/characters`, `/{region}/clan/{id}/members`, `/{region}/friends/{character}`. **Другого пути получить эти данные нет** (по нику их не получить). Если задаче нужны эти данные — вход игрока планируется заранее.

Официально: токены пользователя нужны для **всех эндпоинтов, отдающих данные игры, которые обычно недоступны другим игрокам** (пример из доки: список персонажей игрока). Приложение должно уметь **безопасно хранить секрет и делать запросы сервер-сервер**.

Предусловия: одобренное приложение; зарегистрированный `redirect_uri` (через `/myapps`); серверная часть (обмен кода требует секрета). Device flow нет — даже Discord-боту нужна веб-страница для приёма возврата.

**Шаг 1. Ссылка входа** (в реальной ссылке без переносов строк):

```text
https://exbo.net/oauth/authorize
  ?client_id=<CLIENT_ID>
  &redirect_uri=https://example.com/callback
  &scope=
  &response_type=code
  &state=<случайная строка на каждый вход>
```

- `redirect_uri` должен **точно** совпадать с зарегистрированным (протокол, поддомен, завершающий слэш).
- `scope` — пустой.
- `state` — формально необязателен, но официально «настоятельно рекомендован» для защиты от CSRF. **Всегда используй:** своя случайная уникальная строка на каждый вход; при возврате сверь и **игнорируй запрос**, если не совпала.
- Если пользователь уже вошёл в аккаунт EXBO, ему сразу показывают запрос на авторизацию приложения; если не вошёл — сначала вход, потом запрос. После согласия EXBO редиректит на `redirect_uri` с `code` (и `state`, если передавали).

**Шаг 2. Обмен кода на токены** (на сервере, `application/x-www-form-urlencoded`). Код одноразовый и короткоживущий — обменивай немедленно в обработчике возврата:

```bash
curl -X POST 'https://exbo.net/oauth/token' \
  -d 'client_id=<CLIENT_ID>' \
  -d 'client_secret=<CLIENT_SECRET>' \
  -d 'code=<CODE>' \
  -d 'grant_type=authorization_code' \
  -d 'redirect_uri=https://example.com/callback'
```

Ответ: `access_token`, `refresh_token`, `expires_in`.

**Шаг 3. Обновление:**

```bash
curl -X POST 'https://exbo.net/oauth/token' \
  -d 'client_id=<CLIENT_ID>' \
  -d 'client_secret=<CLIENT_SECRET>' \
  -d 'grant_type=refresh_token' \
  -d 'refresh_token=<REFRESH_TOKEN>' \
  -d 'scope='
```

**Чей токен:** `GET https://exbo.net/oauth/user` с `Authorization: Bearer <токен>` → `id`, `uuid`, `login` и др. Это **аккаунт**, а не персонаж; логин аккаунта ≠ ник персонажа; персонажи берутся отдельно через `/{region}/characters` и на каждом регионе свои.

**Хранение:** пару токенов храни рядом с `uuid` игрока (не с ником). Токен привязан к приложению (`aud` в JWT) — чужой не заработает.

### 4.5. Валидность токенов

- Токены — обычные JWT (RS256), payload читается без сервера (`aud`, `sub`, `exp`, `iat`, `jti`).
- API проверяет payload токена на каждом запросе и возвращает `401`, если токен больше недействителен. Причины помимо истечения срока (официально): игрок **отключил интеграцию** или токен **отозван**. Официальные примеры (демо-токены) имеют `exp` на ~100 лет вперёд.
- **Не полагайся на `exp`.** Токен может умереть раньше: игрок отозвал доступ или EXBO аннулировал токен.
- Единственный надёжный признак — **`401` от API**. Обрабатывай его всегда: для токена пользователя — удалить пару и предложить войти заново (или попробовать refresh).

## 5. Справочник эндпоинтов

Базовый путь: `https://eapi.stalcraft.net/{region}/...`

| Эндпоинт | Токен | Назначение |
|---|---|---|
| `GET /regions` | нет | Список регионов |
| `GET /{region}/auction/{item}/lots` | приложения | Активные лоты предмета |
| `GET /{region}/auction/{item}/history` | приложения | История сделок предмета |
| `GET /{region}/character/by-name/{character}/profile` | приложения | Профиль персонажа по нику |
| `GET /{region}/characters` | **пользователя** | Персонажи владельца токена |
| `GET /{region}/clans` | приложения | Постраничный список кланов |
| `GET /{region}/clan/{clan-id}/info` | приложения | Карточка клана |
| `GET /{region}/clan/{clan-id}/members` | **пользователя** | Состав клана |
| `GET /{region}/emission` | приложения | Статус выброса |
| `GET /{region}/operations/sessions` | нет | Завершённые сессии операций |
| `GET /{region}/friends/{character}` | **пользователя** | Друзья своего персонажа |

### 5.1. Аукцион — лоты

`GET /{region}/auction/{item}/lots`

Единственный способ узнать текущую цену. Общего эндпоинта «все лоты» нет — только по конкретному `id` предмета.

| Параметр | Описание |
|---|---|
| `offset` | Сколько пропустить, по умолчанию 0 |
| `limit` | 0…200, по умолчанию 20. **>200 — это `400`**, а не молчаливое урезание |
| `sort` | `time_created`, `time_left`, `current_price`, `buyout_price` |
| `order` | `asc` / `desc` |
| `additional` | `true` — добавить объект `additional` (игровое состояние предмета). По умолчанию `false` |

Ответ: `total` (всего лотов, а не вернувшихся), `lots[]` с полями `itemId`, `amount`, `startPrice`, `currentPrice`, `buyoutPrice`, `startTime`, `endTime`, `additional` (только при `additional=true`, набор ключей зависит от типа предмета).

Критичные правила:

- **Цена указана за весь лот, а не за штуку.** Цена за штуку = `price / amount`. Забыть поделить — ошибка в тысячи раз на стакающихся предметах.
- `400` на аукционных эндпоинтах может означать, что **предмет не торгуется** — это признак, а не сбой.
- Модули оружия — особый случай (раздел 9): без `additional=true` лот бесполезен.
- Эндпоинт может отдавать **устаревший срез** — см. раздел 7.

### 5.2. Аукцион — история

`GET /{region}/auction/{item}/history`

Параметры: `offset`, `limit` (0…200, по умолчанию 20), `additional`. Сортировка фиксирована — по времени по убыванию.

Ответ: `total`, `prices[]` → `amount`, `price` (за весь лот), `time`.

История — основа «честной цены» (рецепт в разделе 10).

### 5.3. Профиль персонажа

`GET /{region}/character/by-name/{character}/profile`

Ответ: `username`, `uuid`, `status`, `alliance`, `lastLogin`, `displayedAchievements`, `clan` (объект; **поля нет вообще**, если персонаж без клана), `stats[]` (`{id, type, value}`, где `type` — `INTEGER`/`DECIMAL`/`DATE`/`DURATION`).

- `404` — такого ника нет на этом регионе.
- Идентификаторы статистики (`kil`, `dea`, `dis-cra`...) расшифровываются файлом `stats.json` из базы предметов (раздел 8). Угадывать их нельзя.
- `DECIMAL` приходит в экспоненциальной записи (`4.33E8`) — приводи к числу перед показом пользователю.

### 5.4. Персонажи игрока

`GET /{region}/characters` — токен пользователя. Ответ: массив `{information: {id, name, creationTime}, clan: {info, member}}`. С токеном приложения → `401`.

### 5.5. Кланы

`GET /{region}/clans` — `offset`, `limit` (0…200). Ответ: `totalClans`, `data[]` (`id`, `name`, `tag`, `level`, `levelPoints`, `registrationTime`, `alliance`, `description`, `leader`, `memberCount`). На RU несколько тысяч записей — нужна пагинация по 200.

`GET /{region}/clan/{clan-id}/info` — карточка по UUID (`404`, если клана нет).

`GET /{region}/clan/{clan-id}/members` — токен пользователя, выданный игроком, у которого есть персонаж **в этом самом клане**. Ответ: `[]` из `name`, `rank` (`RECRUIT`, `COMMONER`, `SOLDIER`, `SERGEANT`, `OFFICER`, `COLONEL`, `LEADER`), `joinTime`. `401` значит **либо** токен приложения вместо пользовательского, **либо** владелец не состоит в клане — различить по ответу нельзя. Если нужен состав чужого клана — попроси авторизоваться любого его участника.

### 5.6. Выброс

`GET /{region}/emission`

Ответ: `currentStart` (**есть только во время выброса**), `previousStart`, `previousEnd`. Когда выброса нет, ключа `currentStart` в объекте нет вообще. Проверяй **наличие ключа**, а не пустоту строки. Времени следующего выброса в API нет — не придумывай его.

### 5.7. Сессии операций

`GET /{region}/operations/sessions` — **без токена**, единственный эндпоинт с фильтрами по времени.

| Параметр | Описание |
|---|---|
| `username` | Только сессии с этим участником |
| `limit` | 0…**100**, по умолчанию 100 |
| `offset` | Пропуск, по умолчанию 0 |
| `after` / `before` | Сессии, завершённые после / до момента (ISO 8601) |
| `map` | Кодовое имя карты, например `sea_alienation` |
| `sort` | `date_finish` (по умолчанию) или `difficulty` |
| `order` | `asc` / `desc` (по умолчанию `desc`) |

Ответ: `total`, `sessions[]` (`id`, `map`, `startTime`, `endTime`, `difficulty`, `sessionDurationSeconds` (дробное), `difficultyReward`, `participants[]`).

- `id` сессии — больше `Number.MAX_SAFE_INTEGER` (см. раздел 7).
- Статистика участников часто нулевая, поля снаряжения (`armorItemId`, `primaryWeaponItemId`) могут отсутствовать. Это норма. **Не строй средние по нулям** и считай отсутствие поля нормой.

### 5.8. Друзья

`GET /{region}/friends/{character}` — токен пользователя; персонаж должен принадлежать владельцу токена. Ответ: массив ников. `401` — токен приложения либо чужой персонаж.

## 6. Формат ошибок

Два **разных** формата, оба со статусом `400`. Разбирай оба:

```json
// ошибка маршрута
{ "title": "Unknown region: XX", "status": 400, "details": {} }

// ошибка проверки параметра (ключ = имя параметра)
{ "limit": [ { "message": "Limit should be >= 0 and <= 200", "args": {}, "value": 999 } ] }
```

## 7. Ограничения и подводные камни

### 7.1. Три слоя ограничений

Запрос проходит через три независимых слоя. **По коду статуса причину не определить** — два разных `429` требуют противоположных действий.

**Слой 1 — приложение**

| Ограничение | Как выглядит | Что делать |
|---|---|---|
| Квота приложения | `429`, обычно с `Retry-After`, **без** «1015» в теле | Подождать. Адрес ни при чём |
| Потолок страницы | `400` с телом `{"limit":[...]}` | Пагинация по 200 (по 100 для операций) |
| Предмет не торгуется | `400` на оба аукционных эндпоинта | Пометить предмет и больше не опрашивать |
| Права токена | `401` без признаков Cloudflare | Нужен токен пользователя |
| Задержка данных | `200`, но свежайший лот ~10 минут позади | Ничего, это сторона EXBO |

**Слой 2 — Cloudflare** (ограничивает исходящий **адрес**, а не приложение)

| Признак | Код | Причина |
|---|---|---|
| Частота с адреса | `429` + `error code: 1015` | Порог ≈ **22 запроса/сек на один IPv4** (замер 07.08.2026); адреса складываются линейно |
| Отпечаток клиента | `403` | User-Agent, порядок заголовков, TLS-отпечаток |
| Репутация адреса | `403` или челлендж | Хостинг, VPN, анонимайзеры |
| Правило зоны | `403`, `1020` | Путь, метод, заголовки, страна |

- **Не путай два `429`.** С `1015` в теле — виноват адрес, токен исправен (меняй адрес). Без `1015`, с `Retry-After` — виноват токен/квота (жди). Наказывая токен за блокировку адреса, ты выводишь из работы исправные токены.
- **User-Agent решает много.** Замер 07.08.2026: `Python-urllib/3.11` — 49 из 49 запросов получили `403`; `curl/7.88.1` — те же 49 запросов успешны. **Всегда задавай собственный явный User-Agent.** Значение по умолчанию у большинства библиотек — путь к `403`.
- У `eapi.stalcraft.net` **нет AAAA-записи** — IPv6 не работает; «размазывать» лимит по IPv6 бессмысленно.

### 7.2. Задержка данных

Данные аукциона отстают примерно на **10 минут** (наблюдается с 02.07.2026, не менялось). Мгновенных уведомлений нет. **Опрашивай не чаще раза в несколько минут** — чаще бессмысленно и быстрее упирается в лимиты. «Мониторинг в реальном времени» на этом API всегда опаздывает на те же 10 минут.

### 7.3. Устаревший срез (самое коварное)

Симптомы: статус `200`, честный `total`, никакой ошибки. Но параметры `limit`, `offset`, `sort`, `order` **молча проигнорированы**; в ответе всегда ~сотня самых дешёвых лотов, отсортированных по цене **лота**. Для стакающихся предметов порядок «по цене лота» противоположен порядку «по цене за штуку» — выгодных лотов в срезе может не быть вообще.

Как распознать:

- **Верный признак:** ответ обязан быть отсортирован так, как ты просил. Не отсортирован → это срез.
- **Не используй** признак «просили 200, пришло 100»: у предмета с ~100 лотами он не сработает, а при запросе ровно 100 — не сработает никогда.

Лечение: **повторить запрос с другого исходящего адреса**, а не ждать. Замедление не помогает (40 запросов за 3.8 с по нетронутому предмету режим не включили ни разу, замер 08.08.2026).

### 7.4. Прочие ловушки

- **Пагинация:** идти страницами, пока `offset < total` (или `totalClans`). Не использовать «пришло меньше, чем просили» как признак конца — он ложно срабатывает на устаревшем срезе.
- **ID сессий операций** больше `Number.MAX_SAFE_INTEGER`: `JSON.parse` тихо округлит и склеит разные сессии. Читай `id` из сырого текста ответа или используй BigInt (например, парсер с поддержкой big-int / регулярная замена `"id":(\d{16,})` → строка до парсинга).
- **`DECIMAL` в экспоненциальной записи** — приводить к числу и форматировать перед показом.
- **Поле отсутствует ≠ ошибка:** `clan` в профиле, `currentStart` в выбросе, поля снаряжения в сессиях.

### 7.5. Шпаргалка по кодам

```text
429 + "1015" в теле                → адрес.  Сменить адрес, токен исправен
429 + Retry-After, без "1015"      → токен.   Подождать, адрес исправен
403, меняется от User-Agent        → отпечаток клиента
403, одинаков со всех адресов      → правило зоны или права токена
401                                → нужен токен пользователя (или токен протух)
400 на аукционе                    → предмет не торгуется
400 с полем в теле                 → параметр вне допустимого диапазона
404                                → персонажа или клана нет
200, порядок не тот, что просили   → устаревший срез: повторить с другого адреса
```

## 8. База предметов (названия, иконки, характеристики, рецепты)

API оперирует `id` и **не знает названий**: `96mj0` в ответе аукциона превращаешь в «ПП-91 «Кедр»» сам. Всё человекочитаемое — в публичном git-репозитории:

```text
https://github.com/EXBO-Studio/stalcraft-database
```

- Старый адрес `stalzone-database` отвечает `301`-редиректом. Многие HTTP-клиенты в серверном коде за редиректом не идут и получают пустое тело. **Указывай конечный адрес** `stalcraft-database` или включай следование редиректам.

### 8.1. Структура

Верхний уровень — реалм (`ru` или `global`). В каждом реалме:

| Файл/каталог | Содержимое |
|---|---|
| `items/` | JSON-описания предметов по категориям: `items/weapon/submachine_gun/96mj0.json` |
| `icons/` | PNG-иконки с теми же путями |
| `listing.json` | Плоский список всех предметов реалма: путь к описанию, иконке, название, ранг. **Самый полезный файл** |
| `stats.json` | Расшифровка id статистики профиля (id, категория, тип, названия на нескольких языках). Без него профиль не расшифровать |
| `achievements.json` | Достижения |
| `hideout_recipes.json` | Рецепты крафта в убежище, навыки верстаков |
| `barter_recipes.json` | Бартерные обмены у торговцев |

Официальная схема дерева: `<realm>/items/<категория>/<подкатегория>/<id>.json` и `<realm>/icons/<категория>/<подкатегория>/<id>.png`; JSON и иконки названы по `id` предмета. В самой официальной документации в одном и том же дереве встречаются `0n9q.json` и `0N9q.png` (разный регистр) — это пример того, что **регистр `id` нельзя «нормализовать»**: бери пути из `listing.json` и проверяй существование файла, не приводи `id` к нижнему регистру.

### 8.2. Как забирать

1. Один раз скачай `listing.json`:
   `curl -sL https://raw.githubusercontent.com/EXBO-Studio/stalcraft-database/main/ru/listing.json`
2. Пути бери оттуда, файлы читай через `raw.githubusercontent.com` (без лимитов на просмотр):
   `curl -sL https://raw.githubusercontent.com/EXBO-Studio/stalcraft-database/main/ru/items/weapon/submachine_gun/96mj0.json`
3. Не обходи дерево через GitHub API: у неавторизованных запросов лимит 60/час на адрес, на полный обход не хватит.
4. Либо скачай ZIP-архив целиком, если данные нужны редко.
5. Обновляй свой кэш после патчей игры — репозиторий обновляется автоматически, твой кэш нет.

**Официальные примеры запросов к GitHub API** (подставь актуальное имя репозитория; лимит 60 запросов/час без авторизации):

```text
# категории предметов реалма RU
GET https://api.github.com/repos/EXBO-Studio/stalcraft-database/contents/ru/items/
Accept: application/vnd.github+json

# подкатегории оружия
GET https://api.github.com/repos/EXBO-Studio/stalcraft-database/contents/ru/items/weapon

# пистолеты
GET https://api.github.com/repos/EXBO-Studio/stalcraft-database/contents/ru/items/weapon/pistol

# описание конкретного предмета (пистолет 0n9q)
GET https://raw.githubusercontent.com/EXBO-Studio/stalcraft-database/main/ru/items/weapon/pistol/0n9q.json
```

**Иконки на сайте.** Иконку можно подключать прямо с GitHub (официальный пример): `<img src="https://github.com/EXBO-Studio/stalcraft-database/raw/main/ru/icons/weapon/pistol/0n9q.png"/>`. Путь иконки бери из поля `icon` в `listing.json`, а не конструируй из `id`.

### 8.3. Нельзя доверять базе как полной

Часть предметов, которые есть в игре и торгуются, в базе **отсутствует** (пример на 08.08.2026: `y1q9` и `0n9q` нет ни в `ru`, ни в `global`). Правила:

- Отсутствие предмета в базе — **не ошибка твоего кода**. Не роняй обработку.
- Неизвестный `id` показывай **как есть** (а не пустой карточкой и не исключением).
- Обратной связи от EXBO ждать не стоит: планируй так, будто исправлений не будет. При необходимости веди собственный слой недостающих предметов.

### 8.4. Что стабильно, а что нет

- **`id` предмета стабилен и уникален** (в `ru` 2329, в `global` 2312 записей, дублей нет). **Ключ твоей базы — `id`.**
- **Путь к предмету нестабилен:** между патчами предметы переезжают между категориями (пример: `/items/medicine/9mmq.json` → `/items/supply/medicine/9mmq.json`; 129 переездов в одном сравнении). Считай путь временным адресом файла. Если ключом сделать путь, после патча переехавшие предметы выглядят новыми, а старые — удалёнными (теряются иконки, история цен, привязки).
- **У рецептов нет идентификатора** — только `bench`, `category`, `ingredients`, `result`. При этом 24 предмета в `hideout_recipes.json` изготавливаются **несколькими способами**. Не складывай рецепты в словарь по итоговому предмету — потеряешь способы; храни список.

### 8.5. Запись в `listing.json`

```json
{
  "data": "/items/weapon/submachine_gun/96mj0.json",
  "icon": "/icons/weapon/submachine_gun/96mj0.png",
  "name": { "type": "translation", "key": "item.wpn.kedr.name", "args": {},
            "lines": { "ru": "ПП-91 «Кедр»", "en": "PP-91 KEDR", "ko": "PP-91 케드르" } },
  "color": "RANK_NEWBIE",
  "status": { "state": "PERSONAL_ON_USE" }
}
```

### 8.6. Файл описания предмета

Корневые поля: `id` (совпадает с именем файла), `category` (может меняться между патчами), `name` (текстовый объект), `color` (у артефактов — качество, у остальных — ранг: `RANK_NEWBIE`, `RANK_STALKER`, `RANK_VETERAN`, `RANK_MASTER`, `RANK_LEGEND`, `DEFAULT`), `status.state` (`PERSONAL_ON_USE` — привязывается при использовании, `NON_DROP` — не выпадает; объясняет, почему предмета нет на аукционе), `infoBlocks` (остальное описание).

**Текстовые объекты** — любой видимый текст это объект, а не строка. Языки: `ru`, `en`, `es`, `fr`, `ko`.

| Тип | Что делать |
|---|---|
| `translation` | Взять нужный язык из `lines`. Есть устойчивый `key` — ищи характеристики **по нему**, а не по видимому названию |
| `text` | Показать `text` как есть. Иногда пустой |

- Символ `@` внутри переведённой строки — это **перенос строки**, замени его.

**Блоки `infoBlocks`** (тип в поле `type`; незнакомый тип — пропускай, не падай):

| Тип | Содержимое |
|---|---|
| `list` | Необязательный заголовок + `elements` (все характеристики) |
| `text` | Необязательный `title` и текстовый объект `text` (обычно художественное описание) |
| `damage` | Кривая урона оружия: `startDamage`, `damageDecreaseStart`, `damageDecreaseEnd`, `endDamage`, `maxDistance` |

> В официальной документации блок называется `damage-ramp`, но в **реальных файлах** он приходит как `damage`. Сравнение с `"damage-ramp"` никогда не сработает.

**Элементы внутри `list`:**

| Элемент | Поля |
|---|---|
| `numeric` | `name`, `value`, плюс недокументированное `formatted` (готовая строка с единицами на каждом языке) |
| `key-value` | `key`, `value` |
| `range` | `name`, `min`, `max` (например, неисследованный артефакт) |
| `text` | `text` |
| `price` | `currency`, `amount` |
| `item` | `name` (ссылка на другой предмет по названию) |

Ищи характеристики по `name.key` (например, `core.tooltip.info.weight`) — ключ не меняется между патчами и одинаков на всех языках. Для отображения используй `formatted`, чтобы не писать свою таблицу единиц.

Официальные пояснения к элементам: `numeric.value` — число с плавающей точкой (пример: «Вес: 2.5 кг»); `key-value` — оба поля текстовые объекты (пример: «Класс: Рюкзаки и контейнеры»); `range.min`/`max` — числа (пример: «Переносимый вес: [+3; +5]» у неисследованного артефакта); `text`-элемент — как `text`-блок, но внутри списка; `price` — в официальной доке отмечено, что в базе примера может не быть, элемент виден в игре у торговцев; `item` содержит только `name` и по сути как `text`, но несёт иной смысл (название предмета). Блок `damage` описан официально как «damage ramp»: `startDamage` — урон на 0 м, `damageDecreaseStart`/`damageDecreaseEnd` — расстояния (м) начала и конца падения урона, `endDamage` — урон на расстоянии `damageDecreaseEnd`, `maxDistance` — дальность, после которой урона нет. Блок `text` (`title` необязателен) — простой текстовый блок; `text`-объект типа `text` может содержать, например, `"$5"`.

## 9. Модули оружия (особый случай аукциона)

Все модули продаются под одним `id` — **`1pyq`** («Модуль оружия»). Название, редкость и проценты в самом лоте отсутствуют; всё лежит в `additional.attributes`. **Без `additional=true` лот модуля бесполезен** — всегда запрашивай с этим параметром.

### 9.1. Структура лота

```json
{
  "itemId": "1pyq", "amount": 1, "startPrice": 0, "buyoutPrice": 300000,
  "additional": {
    "qlt": 1,
    "attributes": [
      { "type": 1, "statsRandom": -0.45354962, "definitionId": "recoil_suf", "quality": 1 },
      { "statsRandom": -0.89333594, "definitionId": "aiming_speed_modifier_pre", "quality": 1 },
      { "type": 2, "statsRandom": -0.8085954, "definitionId": "marksman" }
    ],
    "it_transf_count": 1
  }
}
```

### 9.2. Поля атрибута

| Поле | Значение |
|---|---|
| `definitionId` | Какой это модуль. Единственное поле, пригодное «как есть» |
| `type` | **Слот**: поля нет → надстройка; `1` → отклонение; `2` → концепт |
| `quality` | Полоса редкости ролла, 0…6. **Поля нет → 0 (обычный)**, а не «неизвестно» |
| `statsRandom` | Позиция внутри полосы. Само по себе ничего не значит (не проценты и не доля) |

**Три поля-омонима — не путать:** `additional.qlt` (редкость предмета целиком = максимум `quality` трёх атрибутов), `attributes[].quality` (полоса одного ролла), `attributes[].type` (**номер слота**, не качество), и `stats[].type` (`positive`/`negative`) в справочнике модулей — польза характеристики, а не знак числа. Фильтрация по `qlt` — это фильтрация по одному (лучшему) роллу.

### 9.3. Слоты и имя предмета

Атрибутов всегда **ровно три**, по одному из каждой группы. Имя собирай по **группам**, а не по индексу в массиве (порядок в ответе не совпадает с порядком в названии):

| `type` | Группа | Место в названии |
|---|---|---|
| нет | Надстройка | первое слово |
| `1` | Отклонение | второе слово |
| `2` | Концепт | в кавычках в конце |

Пример: «Фокусный Уходящий «Снайпер»».

### 9.4. Потенциал (процент, который видит игрок)

Шкала потенциала — **0…190**, не 0…100 (значение «163%» нормально). В API потенциала нет — есть полоса (`quality`) и позиция (`statsRandom`).

| `quality` | Редкость | Потенциал |
|---|---|---|
| 0 | Обычный | 0 — 18.72 |
| 1 | Необычный | 18.72 — 40.25 |
| 2 | Особый | 40.25 — 64.58 |
| 3 | Редкий | 64.58 — 91.72 |
| 4 | Исключительный | 91.72 — 121.67 |
| 5 | Легендарный | 121.67 — 154.43 |
| 6 | Уникальный | 154.43 — 190 |

`statsRandom` — отклонение от середины полосы (0 — центр, ±2 — края):

```javascript
const [lo, hi] = BANDS[attr.quality ?? 0];
const potential = Math.min(190, Math.max(0,
  (lo + hi) / 2 + (hi - lo) / 4 * attr.statsRandom));
```

`statsRandom` может выходить за ±2 (в выборке до -2.95, только в нижнюю сторону). Ограничивай потенциал диапазоном 0…190, а **редкость оставляй такой, какой прислали** — её задаёт `quality`.

### 9.5. Из потенциала — в значения характеристик

```text
value = min + (max - min) * potential / 190
```

`min` — значение при потенциале 0, `max` — при 190. **`min` может быть больше `max`** (у «Уходящего»: 13.087 и 3.272) — это не ошибка данных. Не сортируй их «по-человечески», иначе получишь зеркальные проценты.

### 9.6. Таблица характеристик модулей

В репозитории EXBO таблицы нет (там только название и описание, без `definitionId` и диапазонов). Публичный сводный индекс сообщества (48 модулей, ключ верхнего уровня — `definitionId`):

```text
https://lunar-zone.com/database/STALCRAFT/ru/items/weapon_modules/module/_index.json
```

Запись:

```json
"recoil_suf": {
  "item_id": "n4kx", "group": "deviation", "group_label_ru": "Группа отклонений",
  "title_ru": "Уходящий", "description_ru": "Отдача",
  "stats": [ { "key": "recoil", "name_ru": "Отдача", "type": "negative", "min": 13.087, "max": 3.272 } ]
}
```

- Названия в индексе русские. Для другого языка возьми `item_id` и прочитай `name.lines` из файла модуля (`.../module/n4kx.json`).
- Индекс есть только для `ru`, но `definitionId` и числа от реалма не зависят.
- Нет записи для `definitionId` — это новый модуль после патча: покажи `definitionId` как есть.

### 9.7. Эталонная реализация

```javascript
const BANDS = [[0, 18.72], [18.72, 40.25], [40.25, 64.58], [64.58, 91.72],
               [91.72, 121.67], [121.67, 154.43], [154.43, 190]];
const SLOTS = { 0: 'add-on', 1: 'deviation', 2: 'concept' };

function readRoll(attr, index) {
  const [lo, hi] = BANDS[attr.quality ?? 0];
  const potential = Math.min(190, Math.max(0,
    (lo + hi) / 2 + (hi - lo) / 4 * attr.statsRandom));

  const def = index.modules[attr.definitionId];   // нет записи — новый модуль
  return {
    slot: SLOTS[attr.type ?? 0],                  // нет type = надстройка
    name: def?.title_ru ?? attr.definitionId,
    potential,
    effects: (def?.stats ?? []).map(s => ({
      name: s.name_ru,
      value: s.min + (s.max - s.min) * potential / 190
    }))
  };
}

const rolls = lot.additional.attributes.map(readRoll);
const named = g => rolls.find(r => r.slot === g)?.name;
const title = `${named('add-on')} ${named('deviation')} «${named('concept')}»`;
```

**Самопроверка:** расхождение с тултипом в игре в разы почти всегда означает одно из двух — перепутаны `min`/`max` либо потенциал поделён на 100 вместо 190.

## 10. Рецепты (готовые алгоритмы)

### 10.1. Честная цена предмета

Активные лоты — это хотелки продавцов; реальную цену даёт история сделок.

1. `GET /{region}/auction/{item}/history?limit=200`.
2. Для каждой записи: `price / amount` (цена **за штуку**).
3. Отсортировать, отбросить выбросы с обоих концов (по ~10%).
4. Взять **медиану**, а не среднее.

```javascript
const res  = await fetch(`${BASE}/RU/auction/${item}/history?limit=200`, { headers });
const data = await res.json();

const unit = data.prices.map(p => p.price / p.amount).sort((a, b) => a - b);
const trim = Math.floor(unit.length * 0.1);
const core = unit.slice(trim, unit.length - trim);
const median = core[Math.floor(core.length / 2)];
```

### 10.2. Полная выгрузка

Списочные эндпоинты отдают максимум 200 записей (операции — 100). Иди по `offset`, пока не наберёшь `total` / `totalClans`:

```javascript
let offset = 0, all = [];
const LIMIT = 200;
let r;
do {
  r = await get(`/RU/clans?limit=${LIMIT}&offset=${offset}`);
  all.push(...r.data);
  offset += LIMIT;
} while (offset < r.totalClans);
```

### 10.3. Поиск предмета по названию

В API поиска по названию нет. Решай на своей стороне:

1. Скачай `listing.json` нужного реалма и построй индекс «название → запись» по **всем языкам** из `name.lines`.
2. Ключ — `id` (берётся из имени файла в `data`), путь `data` — лишь адрес файла.
3. Допускай, что предмета в базе может не быть — показывай `id` как есть.
4. Обновляй индекс после патчей.

### 10.4. Устойчивый опрос

- Разделяй `429`: с «1015» → меняй адрес; без «1015» → жди (`Retry-After`). Один обработчик на оба — гарантированно хуже.
- Проверяй, что ответ отсортирован так, как просили. Нет → устаревший срез, повтор с другого адреса.
- Всегда ставь явный `User-Agent`.
- Опрашивай не чаще раза в несколько минут.
- Запоминай предметы с `400` на аукционе и не возвращайся к ним.
- Ограничивай параллелизм: помни про порог ≈22 запроса/сек на IPv4.
- Обрабатывай `401` всегда, независимо от `exp`.

## 12. Чего агент делать не должен

- Не пытаться записывать данные в игру (выставлять/покупать лоты) — API это не поддерживает.
- Не выдумывать время следующего выброса, инвентарь игрока, PvP-статистику — их в API нет.
- Не интерпретировать `statsRandom` как проценты и не делить потенциал на 100.
- Не использовать цену лота как цену за штуку.
- Не угадывать расшифровку идентификаторов статистики — только через `stats.json`.
- Не хранить и не показывать секреты и токены.
- Не наказывать токен за `429` с «1015» (это проблема адреса).
- Не опрашивать API чаще, чем раз в несколько минут и не рассчитывать на данные «в реальном времени».
- Не использовать путь предмета в базе как ключ.
- Не считать отсутствие предмета в базе ошибкой и не падать на неизвестных полях.
- Не продавать и не распространять персональные данные пользователей без их явного согласия (Terms of Use, раздел 13).
- Не использовать API для сценариев, нарушающих закон или EULA игры.
- Не пропускать проверку `state` в OAuth-возврате.
