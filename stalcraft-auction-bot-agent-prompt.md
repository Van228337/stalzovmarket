# Промпт для агента: бесплатный сервис анализа аукциона STALCRAFT (поиск перекупных сделок)

> Как использовать: вставь весь файл как первое сообщение агенту (Claude Code / Cursor / др.) и приложи рядом файл `stalcraft-api-agent-instructions.md` — это нормативный справочник по API EXBO.

---

## 0. Роль и цель

Ты — старший инженер и количественный аналитик. Построй **полностью бесплатный** сервис, который:

1. по официальному API STALCRAFT регулярно собирает активные лоты аукциона и историю сделок;
2. хранит их в бесплатной БД (Supabase Postgres);
3. **сам** считает честную цену, ликвидность, риск и выдаёт сигналы: **что покупать, за сколько, когда и за сколько перепродавать, и почему**;
4. отдаёт компактный **«дайджест рынка» в JSON** (для скармливания нейросети) вместе с готовым промптом для LLM-аналитика;
5. шлёт алерты в Telegram и показывает дашборд.

Пользователь использует результат для перекупства. Твоя задача — давать **честные, откалиброванные оценки с указанием уверенности**, а не обещания прибыли.

## 1. Жёсткие ограничения (нарушать нельзя)

1. **Бюджет 0 ₽/$.** Никаких VPS, платных хостингов, платных API, платных тарифов, подписок, привязки карты. Если для какого-то куска нужна карта — выбери другой путь или спроси пользователя.
2. **Без постоянно работающего сервера.** Бэкенд — это расписание (cron) + бесплатная БД + статический фронтенд.
3. **Только официальный API EXBO**, только чтение. Никакого скрейпинга игрового клиента, автоматизации покупок, обхода ограничений игры. Соблюдай Terms of Use (раздел 13 приложенного справочника). API не умеет покупать/выставлять — не пытайся это эмулировать.
4. **Секреты** (`CLIENT_ID`, `CLIENT_SECRET`, ключи Supabase, токены Telegram/LLM) — только в переменных окружения и GitHub Secrets. Никогда в коде, логах, коммитах, артефактах, дашборде.
5. **Прочитай `stalcraft-api-agent-instructions.md` целиком до написания кода** и следуй ему. Особенно: разделы 3 (регионы), 5 (эндпоинты), 7 (ограничения), 8 (база предметов), 9 (модули оружия), 10 (рецепты).
6. Не выдумывай данные и параметры игры. Чего не знаешь (комиссия аукциона, поведение полей `additional` у конкретных предметов) — **измерь** на реальных ответах или вынеси в конфиг и спроси пользователя.

## 2. Рекомендуемая бесплатная архитектура

Проверено по документации провайдеров (на октябрь 2026); перед стартом перепроверь актуальные лимиты на официальных страницах — они менялись и могут измениться.

| Слой | Решение | Почему / ограничения |
|---|---|---|
| Планировщик + сборщик | **GitHub Actions** (workflow по cron) в **публичном** репозитории | Для публичных репозиториев стандартные раннеры бесплатны без лимита минут; для приватных — только ~2000 мин/мес на Free-плане, на частый опрос не хватит. Минимальный интервал cron — 5 минут, запуски могут запаздывать и иногда пропускаться. Планировщик в публичном репо **отключается после 60 дней без активности** репозитория — нужен keep-alive (см. 9.4) |
| База данных | **Supabase Free** (Postgres) | 500 МБ на проект, проект **приостанавливается после 7 дней неактивности** (регулярные записи сборщика это предотвращают). Нужен строгий бюджет данных (раздел 6) |
| Аналитика | Python внутри того же workflow + SQL-функции/вью в Postgres | Без отдельных серверов |
| Дашборд | Статический сайт на **GitHub Pages** или **Cloudflare Pages** (чтение из Supabase через anon-ключ + RLS только на чтение) | Бесплатный хостинг статики |
| Алерты | **Telegram Bot API** | Бесплатно |
| LLM-анализ | Основной путь: `digest.json` + готовый промпт — пользователь сам вставляет в нейросеть. Опционально: вызов LLM API **только если у пользователя есть бесплатный ключ**, провайдер-независимо через env | Не делай LLM обязательной частью |

**Почему не остальное:** Cloudflare Workers на Free — 10 мс CPU и 50 внешних подзапросов на вызов и всего 5 cron-триггеров на аккаунт (подходит максимум как запасной вариант для малого списка), Vercel Hobby cron слишком редкий, Render/Koyeb free «засыпают», Oracle Always Free — по сути VPS (запрещено условием).

### Главный технический риск — **IP раннера**

API стоит за Cloudflare, который режет **по исходящему адресу и репутации сети** (см. справочник, раздел 7: `403` по репутации/отпечатку, `429`+`1015` по частоте, **устаревший срез** с молча проигнорированными `limit/sort/order`). Раннеры GitHub Actions — адреса дата-центра, их репутация у Cloudflare **заранее неизвестна**. Поэтому:

- **Фаза 0 (обязательная, до всего остального) — тест пригодности канала** (раздел 8). Результат определяет, остаёмся ли на GitHub Actions.
- У GitHub-раннеров адрес меняется от запуска к запуску — это **плюс** против «устаревшего среза» (лечится сменой адреса), но минус для репутации.
- **Запасной вариант без VPS и без денег:** запускать тот же сборщик локально на домашнем ПК/ноутбуке по расписанию (Task Scheduler/cron) — домашний IP обычно имеет лучшую репутацию. Это не сервер, но требует включённого компьютера. Реализуй сборщик так, чтобы он без изменений запускался и в Actions, и локально.
- Второй запасной вариант: Supabase Edge Functions + `pg_cron`/`pg_net` (проверь лимиты и репутацию адреса тестом).
- Если ни один бесплатный канал не проходит тест, **остановись и честно сообщи пользователю**, какой минимальный платный/полубесплатный вариант остаётся. Не обходи защиту Cloudflare хитростями.

## 4. Честные ожидания (закладывай в логику и в тексты сигналов)

- Данные аукциона **отстают на ~10 минут** (в трекере EXBO пользователи сообщают о 10–20). Любой «горячий» лот может быть уже выкуплен. Сигнал — это вероятность, а не гарантия; в сигнале показывай `data_age` и оценку шанса, что лот ещё актуален.
- Лоты, которые видны всем, видят и другие перекупщики. Преимущество — в скорости анализа и дисциплине, а не в секретной информации. Сигналы должны учитывать конкуренцию (не рекомендуй сделки с микро-маржой).
- У истории сделок **нет id лота**, а у активных лотов нет связи с продажами. Связывать их можно только вероятностно (раздел 7.3). Помечай такие связи как вероятностные.
- Никаких фраз вроде «гарантированная прибыль». Каждый сигнал содержит `confidence` и перечень допущений.

## 6. База данных (Supabase Free, бюджет ≤ 400 МБ)

### 6.1. Таблицы (ориентир; можешь улучшить)

```sql
create table items (
  item_id text primary key,                 -- регистрозависимый, непрозрачная строка
  name_ru text, name_en text, category text, rank text,
  icon_path text, listing_path text,        -- пути временные, ключ — item_id
  tradable boolean,                         -- false после 400 на аукционе; перепроверка раз в неделю
  tradable_checked_at timestamptz,
  tier text not null default 'cold',        -- hot | warm | cold
  turnover_30d numeric,                     -- оценка оборота для ранжирования
  updated_at timestamptz default now()
);

create table lots (                         -- «жизненный цикл» лота, а не снимки
  id bigserial primary key,
  region text not null, item_id text not null,
  fingerprint text not null,                -- хэш: item+amount+startPrice+buyoutPrice+startTime+endTime+hash(additional)
  amount int not null, start_price bigint, current_price bigint, buyout_price bigint,
  start_time timestamptz, end_time timestamptz,
  additional jsonb, qlt int, segment_key text,
  first_seen timestamptz not null, last_seen timestamptz not null,
  status text not null default 'active',    -- active | probable_sold | expired_or_cancelled
  sold_match_confidence real,
  unit_buyout numeric generated always as (buyout_price::numeric / nullif(amount,0)) stored,
  unique (region, fingerprint)
);

create table sales (                        -- история сделок, дедуп по составному ключу
  id bigserial primary key,
  region text not null, item_id text not null, segment_key text,
  amount int not null, price bigint not null,
  unit_price numeric generated always as (price::numeric / nullif(amount,0)) stored,
  sold_at timestamptz not null, additional jsonb, additional_hash text not null default '',
  unique (region, item_id, sold_at, price, amount, additional_hash)
);

create table price_rollups (                -- агрегаты по часам
  region text, item_id text, segment_key text, bucket timestamptz,
  n_sales int, units_sold numeric, median_unit numeric, p25_unit numeric, p75_unit numeric,
  active_lots int, min_unit_buyout numeric,
  primary key (region, item_id, segment_key, bucket)
);

create table signals (                      -- текущие рекомендации
  id bigserial primary key, region text, lot_id bigint, item_id text, segment_key text,
  created_at timestamptz default now(), is_current boolean default true,
  buy_unit_price numeric, fair_price numeric, target_sell_unit numeric, floor_sell_unit numeric,
  expected_profit numeric, roi numeric, expected_days_to_sell numeric,
  liquidity_units_per_day numeric, confidence real, score numeric,
  data_age_min numeric, reasons jsonb, caveats jsonb
);

create table collector_runs (               -- здоровье сборщика
  id bigserial primary key, started_at timestamptz default now(), finished_at timestamptz,
  workflow text, requests int, ok int, http_400 int, http_401 int, http_403 int,
  http_429_1015 int, http_429_quota int, stale_slices int, retries int, runner_ip_hash text, notes jsonb
);
```

Данные пишутся через **upsert** (идемпотентно): повторный запуск не плодит дубли.

### 6.2. Бюджет данных (обязательно реализуй и измерь)

- Хранить **жизненные циклы лотов**, а не снимок каждого лота каждые 5 минут.
- Сырые лоты со статусом не `active` — хранить N дней (по умолчанию 14), затем удалять; важные агрегаты остаются в `price_rollups`.
- `sales` для hot-списка — 90 дней; для остальных — 30 дней; старше — удалять после агрегации.
- `price_rollups` — по часам 30 дней, затем по дням без срока.
- Ежедневная задача `maintenance` считает размер БД (`pg_database_size`) и таблиц; при > 350 МБ — шлёт алерт и сокращает ретеншн; при > 450 МБ — **останавливает запись** сырья.
- Приложи в `DECISIONS.md` расчёт: сколько байт на строку × строк/сутки × дней хранения = итоговый размер.

### 6.3. Безопасность

- RLS включена на всех таблицах. Анонимный ключ (фронтенд) — **только `select`** на `signals`, `price_rollups`, `items` и безопасных вью. Запись — только `service_role` из сборщика.
- `service_role` ключ никогда не попадает в браузерный код.

### 6.4. Подключение сборщика к БД

- Через Supabase REST/RPC по HTTPS (PostgREST) **или** через пулер соединений Supabase. Прямое подключение к хосту БД на бесплатном плане может быть только по IPv6, а раннеры GitHub — IPv4: **проверь на практике** и выбери рабочий путь (пулер по IPv4 либо PostgREST). Записывай пачками (batch upsert), не по одной строке.

## 7. Сбор данных и аналитика

### 7.1. Сборщик (правила из справочника — выполнять все)

- Базовый URL и домен настраиваются (`stalcraft.net` по умолчанию, запасной — `stalzone.com`).
- Авторизация — заголовки `Client-Id` / `Client-Secret` (токен приложения).
- **Всегда явный `User-Agent`** (например `stalcraft-market-bot/1.0 (contact: <email>)`), без значений по умолчанию библиотеки.
- **Глобальный ограничитель скорости** (по умолчанию ≤ 5 запросов/сек суммарно, конкурентность 4, джиттер), настраиваемый. Порог ≈ 22 rps/IPv4 — это потолок, к которому приближаться нельзя.
- Различай два `429`: с `1015` в теле — проблема адреса (прервать запуск, пометить, повторить в следующем запуске с другого раннера); без `1015` + `Retry-After` — квота приложения (подождать). Не смешивай.
- **Детектор устаревшего среза:** после каждого запроса лотов с `sort`/`order` проверяй, что ответ реально отсортирован так, как просили; не отсортирован — отбрось ответ, посчитай `stale_slices`, повтори позже с другого адреса. **Не** ловить по числу записей.
- `400` на аукционных эндпоинтах → `items.tradable=false`, больше не опрашивать (перепроверка раз в неделю).
- `401` → остановить запуск, алерт (токен недействителен).
- Цены — **всегда за штуку**: `price / amount`.
- Пагинация только по `offset` до `total`; `limit ≤ 200`.
- Неизвестный `item_id` (нет в базе предметов) — показывать как есть, не падать.
- Разбор терпим к неизвестным полям.
- Каждый запуск пишет строку в `collector_runs` (метрики здоровья). Дашборд показывает «возраст последних данных» и долю ошибок.

### 7.2. Тиры и расписание опроса

- Единоразовая **инициализация**: из `listing.json` (реалм `ru` для региона `RU`, `global` для остальных) загрузи каталог; для каждого `item_id` один запрос `history?limit=200` (разбей на куски по запускам, в рамках лимитов) → оцени оборот (`units_sold`, `sum(price)` за период) и торгуемость (`400` → не торгуется). Ранжируй по обороту.
- **hot** (по умолчанию топ ≤ 150 предметов по обороту/ликвидности + явный watchlist): опрос лотов каждые ~5 мин, история — раз в 15–30 мин.
- **warm**: раз в час. **cold**: раз в сутки или по запросу.
- Размеры тиров и интервалы — в `config.yaml`; автопродвижение/понижение по обороту раз в сутки.
- Для hot для **экономии запросов** запрашивай лоты с `sort=buyout_price&order=asc&limit=…` и только нужную глубину страницы (дешёвая часть рынка — там сделки).
- Модули оружия `1pyq` и артефакты/предметы с состоянием — запрашивай с `additional=true` (см. 7.4).

### 7.3. Жизненный цикл лота и вероятностная связь с продажей

- `fingerprint` лота = хэш от (`item_id`, `amount`, `startPrice`, `buyoutPrice`, `startTime`, `endTime`, нормализованный `additional`).
- Новый fingerprint → вставка (`first_seen`). Виден снова → `last_seen`. Исчез из выдачи полностью просмотренного предмета → кандидат на закрытие.
- Закрывай как `probable_sold`, если в `sales` есть сделка того же предмета с тем же `amount`, ценой (в пределах допуска) и временем в окне вокруг исчезновения; иначе `expired_or_cancelled`. Храни `sold_match_confidence`. **Закрывать лот как исчезнувший можно только если коллекция по предмету была полной** (не усечённый срез, не ошибка).
- Эта статистика даёт эмпирическую оценку «**какая доля лотов по цене X реально продаётся и за сколько часов**» — основа реалистичных прогнозов времени продажи.

### 7.4. Сегментация цены (критично для «жёсткого» анализа)

Цена зависит не только от `item_id`. Определи `segment_key` на основе реальных данных (сэмплируй `additional=true` по разным типам предметов и **зафиксируй найденные ключи в `DECISIONS.md`**):

- **Стакающиеся расходники/материалы:** сегмент = `item_id`; всё считается за штуку.
- **Артефакты и улучшаемое снаряжение:** сегмент по качеству (`qlt`) и уровню заточки/улучшения (ключи — найти в `additional`, не угадывать). Считай цены **отдельно по сегментам**; смешивание сегментов — главная причина ложных «выгодных» лотов.
- **Модули оружия (`1pyq`):** разбери по разделу 9 справочника (слоты, `quality`, `statsRandom` → потенциал 0…190; таблица характеристик из `_index.json`). Сегмент = (`definitionId` трёх слотов или хотя бы концепт + отклонение + надстройка) и полоса потенциала. Цену модуля моделируй как функцию потенциала и редкости (простая монотонная регрессия/изотоническая по сделкам); при нехватке данных — повышай неопределённость и снижай `confidence`. **Юнит-тесты на числах из справочника** (Фокусный/Уходящий/«Снайпер»: потенциалы ≈ 24.68 / 27.04 / 5.58, эффекты +2.02% / +11.69% / +1.34%).
- Неизвестный тип `additional` → сегмент = `item_id` + пометка `segmentation_unknown` в `caveats` и сниженная уверенность.

### 7.5. Честная цена и метрики (на сегмент)

Считай по `sales` (цена **за штуку**), окнами 24ч / 3д / 7д / 30д:

- Взвешенная по свежести (период полураспада настраиваемый, по умолчанию 3 дня) **медиана** после усечения выбросов (по 10% с краёв) + квартили P25/P75, `MAD/median` как волатильность.
- Минимальный размер выборки (по умолчанию ≥ 30 сделок за окно); меньше — расширяй окно и снижай `confidence`; совсем мало — «недостаточно данных», сигналов нет.
- **Ликвидность:** проданных штук в сутки, сделок в сутки, доля времени без сделок.
- **Давление предложения:** число и суммарный объём активных лотов дешевле/равных целевой цене продажи; `ожидаемые_дни_до_продажи ≈ объём_активных_дешевле_цели / штук_в_сутки` (уточняй эмпирикой из 7.3).
- **Тренд:** отношение медианы 24ч к 7д, наклон EMA; режим «рост / боковик / падение / всплеск».
- **Детектор всплесков и манипуляций:** если недавние сделки резко выше 7-дневной медианы без роста объёма — не доверяй «свежей высокой цене», в `caveats`.
- **Сезонность:** день недели × час суток (если данных достаточно) — используй для рекомендаций «когда выставлять».

### 7.6. Сигнал «купить» (формулы — в `analytics/`, пороги — в `config.yaml`)

Для каждого активного лота (`buyout_price` > 0):

```
buy_unit        = buyout_price / amount
sell_target     = quantile(sales_unit, q_target)         # по умолчанию P50 за 3д, с поправкой на тренд
sell_floor      = quantile(sales_unit, q_pessimistic)    # по умолчанию P25 — пессимистичный сценарий
net_sell(x)     = x * (1 - AUCTION_FEE_RATE) - LISTING_FEE_per_unit
profit_expected = (net_sell(sell_target) - buy_unit) * amount
profit_floor    = (net_sell(sell_floor)  - buy_unit) * amount
roi             = profit_expected / (buy_unit * amount)
```

Рекомендуй покупку, только если **одновременно**: `profit_floor ≥ 0` (или заданный минимум), `profit_expected ≥ MIN_PROFIT_ABS`, `roi ≥ MIN_ROI`, ликвидность ≥ порога, `ожидаемые_дни_до_продажи ≤ MAX_HOLD_DAYS`, `confidence ≥ MIN_CONFIDENCE`, лот не помечен как подозрительный (всплеск/тонкая выборка), сумма не превышает лимит на сделку от капитала.

**Ранжирование:** по риск-скорректированной доходности на единицу времени и капитала (`expected_profit_per_day`, `roi`, `confidence`), с учётом общего капитала (набор сделок под бюджет — жадно/рюкзак).

Для **каждого сигнала** обязательны:

- `buy_max_unit` (максимальная цена за штуку, при которой сделка ещё проходит пороги);
- `target_sell_unit` и `floor_sell_unit` (за штуку), **рекомендуемая цена выставления** и **когда** (окно по сезонности/тренду), `expected_days_to_sell`;
- `reasons[]` — человекочитаемое «почему» с цифрами (пример: «Цена за штуку 412 против медианы 3д 480 (n=214), ликвидность 36 шт/сут, активного предложения ниже 480 — 90 шт ≈ 2.5 дня; тренд боковой, волатильность 7%»);
- `caveats[]` — допущения и риски (возраст данных ~10 мин, малая выборка, сегментация неизвестна, всплеск цены, конкуренция);
- `confidence` 0…1 с формулой в коде и описанием в README.

Также выдавай сигналы **«продавать»** (по вашим позициям, если пользователь их вводит вручную через таблицу `positions` / конфиг: купил за X, держу N шт — подскажи цену выставления и когда снижать) и **«избегать»** (рынок падает/манипулируется).

### 7.7. Бэктест (обязателен до того, как доверять сигналам)

- На накопленных `sales` и срезах лотов проиграй правила 7.6 в прошлом: сколько «сигнальных» лотов реально ушло, за сколько часов, по какой цене относительно `sell_target`, каково распределение фактической доходности (с комиссией).
- Выводи метрики: доля прибыльных, средняя/медианная доходность, просадка, чувствительность к порогам, калибровка `confidence` (сигналы с уверенностью 0.8 действительно прибыльны ~80%?).
- Если бэктест показывает отсутствие преимущества — **скажи об этом прямо** и предложи, какие пороги/сегменты улучшить. Не подгоняй под красивую цифру.

## 8. Фазы работ и контрольные точки (останавливайся и отчитывайся после каждой)

**Фаза 0 — Проверка канала (≤ 1 сессия).** Репозиторий-скелет + одноразовый workflow, который из раннера GitHub: (а) дёргает `GET /regions`; (б) 40–100 запросов `lots` с `sort`/`order` по нескольким предметам с явным `User-Agent`, на скорости 3–5 rps; (в) считает `403`, `429`+`1015`, `429` без `1015`, долю устаревших срезов (по проверке сортировки); (г) пишет итог в лог. Повтори запуск 3–5 раз (разные раннеры/адреса). Критерий успеха: стабильно `200`, доля устаревших срезов не критична (лечится повтором), нет массовых `403`. Затем протестируй запись в Supabase из раннера (путь IPv4). **Отчёт пользователю:** проходим ли мы на GitHub Actions; если нет — переходим на запасной вариант (раздел 2).

**Фаза 1 — Данные.** Миграции, каталог предметов, инициализация тиров, сборщик лотов/истории, идемпотентные upsert-ы, `collector_runs`, ретеншн, проверка размера БД.

**Фаза 2 — Аналитика.** Сегментация, честная цена, ликвидность, сигналы, жизненный цикл лотов, модули оружия, юнит-тесты.

**Фаза 3 — Выход.** `digest.json`, промпт LLM-аналитика, Telegram-алерты (с дедупликацией: не слать один и тот же лот дважды, лимит алертов в час), дашборд.

**Фаза 4 — Бэктест и калибровка.** Раздел 7.7, настройка порогов, документация.

**Фаза 5 — Эксплуатация.** `RUNBOOK.md`: как смотреть здоровье, что делать при `401`/`403`/`429`, при заполнении БД, при отключении расписания, при смене домена/эндпоинтов.

## 9. Workflows GitHub Actions (требования)

1. Все workflow: `concurrency` с отменой/очередью, чтобы запуски не накладывались; `timeout-minutes`; `permissions` минимальные; секреты — через `secrets.*`.
2. `collect-hot`: cron `*/5 * * * *` (учитывай, что запуск может запаздывать; сборщик должен быть идемпотентным и устойчивым к пропускам; хранить `fetched_at`).
3. Бюджет времени запуска: уложись в ≤ 3–4 минуты; при превышении лимитов — продолжение в следующем запуске (курсор прогресса в БД).
4. **Keep-alive расписания:** в публичных репозиториях cron отключается после 60 дней без активности — реализуй ежемесячную защиту и проверь её работоспособность; задокументируй ручное включение в RUNBOOK.
5. Репозиторий публичный → в нём **не должно быть секретов и приватных данных**; пороги/стратегию, которые пользователь не хочет раскрывать, вынеси в таблицу `config` в Supabase или в Secrets (спроси пользователя; по умолчанию — предупреди, что код стратегии будет виден всем).
6. Артефакты/логи без секретов; в логах хэш IP раннера, а не сам IP.

## 10. Дашборд (статический)

Страницы: **Сигналы** (таблица с цены/прибыли/уверенности/«почему», фильтры, сортировка, иконки предметов из базы предметов), **Предмет** (график цены сделок, медиана/квартили, объём, активные лоты, сегменты), **Здоровье** (последний успешный сбор, возраст данных, доли ошибок, размер БД), **Настройки** (только чтение конфигурации). ## 12. Требования к качеству

- **Тесты:** юнит-тесты для формул (честная цена, усечение, потенциал/характеристики модулей, комиссия, fingerprint, детектор устаревшего среза, разбор ошибок двух форматов, ID сессий не нужны, но парсер терпим к лишним полям). Интеграционный тест на демо-API (`dapi`, публичные демо-ключи).
- **Идемпотентность и устойчивость:** повторный запуск не портит данные; сбой в середине не оставляет «полузакрытых» лотов; частичные ответы не приводят к закрытию лотов.
- **Наблюдаемость:** метрики здоровья в БД, алерт в Telegram при: нет свежих данных > 30 мин, всплеске `403`/`429`, `401`, размере БД.
- **Документация:** `README.md` (запуск за 10 минут, настройка секретов, как получить доступ к API), `RUNBOOK.md`, `DECISIONS.md` (все найденные факты об API и принятые решения).
- **Не усложняй:** сначала простой работающий конвейер на 20–50 предметах, затем масштабирование.

## 13. Критерии приёмки

1. Фаза 0 пройдена и результат задокументирован (какой канал выбран и почему).
2. Сборщик работает по расписанию бесплатно (GitHub Actions или выбранная альтернатива) минимум 48 часов без ручного вмешательства; `collector_runs` показывает долю успешных запросов и устаревших срезов.
3. БД не превышает бюджет; ретеншн и защита от переполнения работают.
4. Для hot-предметов есть актуальные `sales`, `lots` с жизненным циклом и `price_rollups`.
5. Сигналы содержат все обязательные поля (раздел 7.6), включая «почему» и `caveats`, с честной `confidence`.
6. `digest.json` и `prompts/llm_analyst.md` готовы; на тестовом дайджесте LLM выдаёт осмысленный разбор без выдуманных цифр.
7. Бэктест выполнен и отчёт выложен; если преимущества нет — это сказано явно.
8. Дашборд открывается с бесплатного хостинга и читает данные только через anon-ключ с RLS.
9. В репозитории нет секретов.
