# Корректировка №1 к промпту агента: комиссия 5% и отслеживание только выбранных предметов

> **Приоритет:** этот файл **заменяет и дополняет** `stalcraft-auction-bot-agent-prompt.md`. Если пункты противоречат — действует этот файл. Всё, что здесь не упомянуто, остаётся как в основном промпте.
> Справочник по API (`stalcraft-api-agent-instructions.md`) по-прежнему обязателен к прочтению.

---

## 1. Что изменилось (кратко)

1. **Комиссия аукциона — 5%** (подтверждено пользователем).
2. **Нет автоматического охвата ассортимента.** Сервис **не** строит «горячие/тёплые/холодные» тиры по сотням предметов и **не** обходит весь каталог. Опрашиваются **только предметы, которые пользователь сам добавил** в список отслеживания.
3. **Новый интерфейс:** поиск по базе предметов EXBO → добавление в список отслеживания → настройка порогов по каждому предмету.
4. Следствие: нагрузка на API и размер БД падают на порядок, можно хранить историю дольше и опрашивать чаще.

## 2. Комиссия и формулы прибыли

В `config.yaml`:

```yaml
auction_fee_rate: 0.05        # 5% — подтверждено пользователем
listing_fee: 0                # ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ: есть ли залог/сбор при выставлении лота
fee_applies_to: sale_price    # ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ: 5% удерживается с цены продажи (выкупа)
```

- Чистая выручка за штуку: `net_sell(x) = x * (1 - 0.05) - listing_fee_per_unit`.
- **Безубыточность:** цена продажи должна быть не ниже `buy_unit / 0.95 ≈ buy_unit × 1.0526`, то есть минимум **+5,26%** к цене покупки только чтобы выйти в ноль. Все пороги по умолчанию должны быть **заметно выше**: `min_roi` по умолчанию 0.10 (после комиссии), настраивается глобально и по каждому предмету.
- Пока пользователь не подтвердил два пункта выше (`listing_fee`, `fee_applies_to`), агент использует значения по умолчанию и **явно пишет в каждом сигнале** в `caveats`: «комиссия принята как 5% с цены продажи, сбор при выставлении = 0 (не подтверждено)». Один уточняющий вопрос пользователю (разрешён в Фазе 0): «Есть ли при выставлении лота залог или сбор, и с какой суммы берётся 5% — с цены выкупа или с текущей ставки?»
- Во всех формулах основного промпта (раздел 7.6) используй `net_sell` с этими параметрами; юнит-тесты на комиссию обязательны (например, купил 1000, продал 1100 → чистыми 1045 → прибыль 45, ROI 4,5%).

## 4. Каталог предметов (для поиска)

Каталог нужен только как **справочник для поиска и отображения**, а не как список для опроса.

### 4.1. Синхронизация

- Workflow `sync-catalog.yml`: раз в сутки (и вручную `workflow_dispatch`) скачивает `listing.json` реалма (`ru` для региона `RU`, `global` для остальных) с `raw.githubusercontent.com` (конечный адрес репозитория `stalcraft-database`, редиректы включены) — **один запрос**, без обхода дерева через GitHub API.
- Результат кладётся в таблицу `items` (≈2300 строк, это копейки по размеру) **и** в статический файл `catalog.json` для фронтенда (минимальные поля: `id`, названия на ru/en, `category`, `rank`/`color`, путь иконки, `status.state`). Размер файла сжимай (gzip на хостинге) и следи, чтобы он оставался разумным (сотни КБ).
- Ключ — `item_id`. Путь к описанию и иконке — временные, обновляются при каждой синхронизации (предметы переезжают между категориями).
- Для поиска хранится нормализованное поле `search_text` (все названия на всех языках, нижний регистр, `ё → е`, без «ёлочек» и спецсимволов).

### 4.2. Известные дыры каталога (учесть в UI)

- Некоторые торгуемые предметы **отсутствуют** в базе (в справочнике: `y1q9`, `0n9q`). Поэтому обязателен режим **«Добавить по ID вручную»** (раздел 6.3) — иначе такие предметы вообще нельзя отслеживать.
- `status.state` из `listing.json` (`PERSONAL_ON_USE`, `NON_DROP` и т.п.) — это **подсказка**, что предмет, вероятно, не продаётся на аукционе, но не окончательный вердикт. Реальный признак — `400` от аукционного эндпоинта (раздел 5.3).
- Модули оружия на аукционе все идут под одним `id` `1pyq` — в каталоге они как отдельные предметы, но для аукциона нужен именно `1pyq` (см. раздел 6.4).

## 5. Опрос только по списку отслеживания (замена раздела 7.2)

### 5.1. Таблица

```sql
create table watchlist (
  id bigserial primary key,
  region text not null default 'RU',
  item_id text not null,
  alias text,                                  -- свой ярлык (особенно для предметов без названия в базе)
  enabled boolean not null default true,
  poll_interval_min int not null default 5 check (poll_interval_min >= 5),      -- лоты
  history_interval_min int not null default 30 check (history_interval_min >= 5),
  -- индивидуальные пороги (null = брать из config.yaml)
  min_roi numeric, min_profit_abs numeric, max_buy_unit numeric,
  max_capital_share numeric, min_confidence real,
  filters jsonb not null default '{}',         -- фильтры сегмента: качество, уровень, для модулей — слот/потенциал (см. 6.4)
  note text,
  -- служебные поля сборщика
  tradable boolean, tradable_checked_at timestamptz,
  backfill_done boolean not null default false,
  last_lots_at timestamptz, last_history_at timestamptz,
  next_lots_at timestamptz, next_history_at timestamptz,
  added_at timestamptz not null default now(),
  unique (region, item_id)
);
```

### 5.2. Правила сборщика

- В начале каждого запуска сборщик читает **только** `watchlist where enabled`. Предметы вне списка не опрашиваются никогда.
- Запуск по cron каждые 5 минут обрабатывает предметы, у которых `next_lots_at <= now()` / `next_history_at <= now()`. Это позволяет разным предметам иметь разные интервалы (минимум 5 минут из-за GitHub Actions и задержки данных ~10 минут; чаще бессмысленно).
- **Бюджет запросов** (считай и логируй): `запросов за запуск ≈ N_лотов_due + N_истории_due`. По умолчанию ограничитель ≤ 3 запроса/сек; при списке до ~100 предметов уложиться в запуск легко. Мягкий лимит размера списка в конфиге (`watchlist_soft_limit: 100`): при превышении UI показывает предупреждение, жёсткий лимит (`watchlist_hard_limit: 200`) блокирует добавление. Если не успеваем — приоритет по `last_*_at` (самые давние первыми), остальное в следующем запуске.
- Все правила сборщика из основного промпта (раздел 7.1: `User-Agent`, различение `429`, детектор устаревшего среза, цены за штуку, терпимый разбор) остаются в силе.
- Для предметов со стопками запрашивай лоты с `sort=buyout_price&order=asc` и **достаточной глубиной** (пагинация до `limit=200`, несколько страниц, если нужен полный срез предложения ниже цели); не усечённый срез — условие для закрытия лотов (раздел 7.3 основного промпта).

### 5.3. Проверка торгуемости при добавлении

Заранее проверять все предметы нельзя. Вместо этого:

- При первом опросе нового предмета сборщик делает один пробный запрос `lots?limit=1`. Ответ `400` → `watchlist.tradable=false`, опрос прекращается, UI показывает «не торгуется на аукционе» (пользователь может удалить или оставить; перепроверка раз в неделю). `200` → `tradable=true`.
- Ошибка неверного `item_id` и «не торгуется» дают одинаковый `400` — различай по тому, есть ли id в каталоге: нет в каталоге и `400` → «не найден / не торгуется, проверь ID».

### 5.4. Первичная загрузка истории при добавлении (backfill)

- После первой успешной проверки сборщик подтягивает историю сделок страницами по 200 (`offset`) до лимита `backfill_max_records` (по умолчанию 1000, настраивается; общая глубина у популярных предметов — тысячи записей) и ставит `backfill_done=true`. Это даёт честную цену сразу, а не через неделю накопления.
- Для предметов с `additional` (артефакты, модули) запрашивай историю с `additional=true`, если эндпоинт его отдаёт, и сегментируй цену (раздел 7.4 основного промпта).
- Задержка: новый предмет начинает отображаться в течение ~5–10 минут (до следующего запуска). UI должен честно показывать статус «ожидает первого сбора» — браузер не может дёргать API игры напрямую (секрет приложения).

## 6. Интерфейс выбора отслеживаемых предметов

Статический фронтенд, доступ **только после входа** (раздел 8).

### 6.1. Поиск по каталогу

- Поле поиска по названию (все языки из каталога: ru/en/es/fr/ko), регистр и `ё/е` игнорируются, поиск по подстроке и по началу слов, терпимость к опечаткам по возможности (лёгкая нечёткая сопоставка на клиенте по `catalog.json`; без тяжёлых зависимостей).
- Поиск по `item_id` напрямую.
- Фильтры: категория/подкатегория, ранг (`RANK_*`), «показывать только предметы, которые, вероятно, торгуются» (по `status.state`, как подсказка), «уже в списке отслеживания».
- Результат: иконка (из репозитория базы предметов, путь из `icon`), название на выбранном языке, категория, ранг (цветом), `item_id`, бейдж статуса («возможно не торгуется»), кнопка **«Отслеживать»**.
- Неизвестный `id` и предмет без иконки — отображать как есть, без падения.

### 6.2. Управление списком отслеживания

- Таблица отслеживаемых предметов: иконка, название/alias, статус (ожидает сбора / активен / не торгуется / пауза), возраст последних данных, текущая медианная цена за штуку, лучший сигнал по предмету.
- Действия: пауза/возобновление, удаление, редактирование интервалов опроса и индивидуальных порогов (`min_roi`, `min_profit_abs`, `max_buy_unit`, `max_capital_share`, `min_confidence`), заметка, alias.
- Массовые действия: добавить несколько предметов из результатов поиска, поставить на паузу всё.
- Валидация: интервалы не меньше 5 минут; предупреждения при превышении мягкого лимита; при превышении жёсткого — запрет добавления.
- Импорт/экспорт списка отслеживания в JSON (резервная копия).

### 6.3. «Добавить по ID вручную»

Обязательная функция (в каталоге есть дыры): поле для ввода `item_id` (**регистр сохранять**, не приводить к нижнему), необязательный alias. Запись создаётся со статусом «проверяется»; сборщик выполнит пробный запрос (5.3). Результат («торгуется / не торгуется / ID не найден») показывается в таблице отслеживания.

### 6.4. Особые предметы

- **Модули оружия (`1pyq`):** на аукционе это один `id`, поэтому в списке отслеживания он добавляется как «Модуль оружия (1pyq)» с `filters` (JSON): например, нужные концепты/отклонения/надстройки по `definitionId`, минимальный потенциал, минимальная полоса `quality`. Сборщик забирает лоты с `additional=true`, разбирает их по разделу 9 справочника и **сохраняет/анализирует только подходящие под фильтры** (остальное отбрасывается до записи в БД, чтобы не раздувать базу).
- **Артефакты и улучшаемое снаряжение:** фильтры по `qlt` и уровню улучшения (ключи определить по реальным `additional`, зафиксировать в `DECISIONS.md`); цена считается по сегментам.
- Для обычных стакающихся предметов фильтров нет.

### 6.5. Что показывает дашборд теперь

- **Сигналы** — только по отслеживаемым предметам, с «почему», `buy_max_unit`, ценами продажи и риском.
- **Предмет** — график сделок за штуку, медиана/квартили, объём, активные лоты, сегменты, сигналы по нему, история ваших порогов.
- **Список отслеживания** (6.2) и **поиск** (6.1).
- **Здоровье** — последний сбор по каждому предмету, доля ошибок, размер БД.
- **Дайджест** (`digest.json`) формируется **только из отслеживаемых предметов** и теперь меньше (обычно единицы–десятки КБ), поэтому в него можно включать больше деталей по каждому предмету: распределение цен, глубину предложения, последние сделки.

## 7. Бюджет данных (замена раздела 6.2 основного промпта)

Размер списка маленький, поэтому ограничения мягче, но защита остаётся:

- `sales` по отслеживаемым предметам — хранить **180 дней** (настраивается), затем агрегировать в `price_rollups` и удалять сырьё.
- Завершённые лоты (`probable_sold`, `expired_or_cancelled`) — **30 дней**, затем удалять.
- `price_rollups` по часам — 90 дней, затем по дням без срока.
- Предметы, удалённые из списка отслеживания: данные хранить N дней (по умолчанию 30), потом чистить; в UI — кнопка «удалить вместе с данными».
- Сохраняются защита от переполнения и ежедневный расчёт размера БД из основного промпта (алерт при > 350 МБ, остановка записи сырья при > 450 МБ). В `DECISIONS.md` приложи пересчёт под реальный размер списка (например, 30 и 100 предметов).
- Каталог `items` (~2300 строк) — постоянно; он мал.

## 8. Доступ и безопасность (изменение раздела 6.3 основного промпта)

Раз в интерфейсе есть запись (список отслеживания) и приватные сигналы, а репозиторий публичный (anon-ключ и URL Supabase окажутся в статическом сайте и их увидит любой), **анонимный доступ ко всему, кроме каталога, закрыть**:

- Включить **Supabase Auth**; **отключить публичную регистрацию**; создать единственного пользователя-владельца (вход через GitHub OAuth или одноразовый код на почту — выбрать рабочий вариант и проверить лимиты почтовой рассылки на бесплатном плане).
- RLS на всех таблицах: чтение и запись `watchlist`, `positions`, `config`, чтение `signals`, `lots`, `sales`, `price_rollups`, `collector_runs` — **только аутентифицированному владельцу** (политика по `auth.uid()` владельца, UUID прописывается миграцией из переменной окружения, а не хардкодится в публичном репозитории).
- Анонимный ключ может читать **только** публичный каталог `items` (или он вообще отдаётся статическим `catalog.json` без обращения к БД).
- `service_role` — только сборщик/аналитика (GitHub Secrets). В браузер не попадает никогда.
- Сигналы и дайджест публиковать **только** за аутентификацией; не выкладывать `digest.json` статическим файлом в публичный хостинг. Для «скормить нейросети» — кнопка «Скопировать дайджест» / «Скачать JSON» в интерфейсе после входа.
- Приватные пороги стратегии не хранить в публичных файлах репозитория (в `config.yaml` — только значения по умолчанию, рабочие пороги — в таблице `config`/`watchlist` под RLS).

## 9. Обновлённые фазы

**Фаза 0 — Проверка канала.** Как в основном промпте, но на 3–5 предметах (из демо или первых добавленных). Плюс один вопрос про `listing_fee` и базу начисления 5%.

**Фаза 1 — Каталог и список отслеживания (вместо старой Фазы 1).** Миграции (`items`, `watchlist`, остальное из основного промпта без тиров), `sync-catalog`, RLS и Auth, сборщик по `watchlist` (лоты, история, пробная проверка торгуемости, backfill), `collector_runs`, ретеншн.

**Фаза 2 — Аналитика.** Как в основном промпте (сегментация, честная цена, сигналы, жизненный цикл лотов, модули), но только по отслеживаемым; пороги — с индивидуальными переопределениями из `watchlist`; комиссия 5%.

**Фаза 3 — Интерфейс и выход (вместо старой Фазы 3).** Вход (Auth), поиск по каталогу, управление списком, ручное добавление по ID, фильтры модулей/артефактов, страницы сигналов/предмета/здоровья, дайджест «из выбранных», алерты в Telegram (по умолчанию по всему списку, опционально выключаются по предмету).

**Фазы 4–5** — без изменений (бэктест, эксплуатация), но бэктест считать по отслеживаемым предметам и учитывать 5% комиссию.

## 10. Дополнения к критериям приёмки

1. Поиск находит предметы по русскому и английскому названию, по `item_id`, с учётом `ё/е` и регистра; фильтры по категории и рангу работают.
2. Предмет добавляется в список отслеживания из интерфейса, и в течение 1–2 циклов (≈ 5–15 минут) по нему появляются данные; интерфейс честно показывает статус ожидания.
3. Предмет, отсутствующий в каталоге (например, `y1q9`), добавляется через «по ID вручную» и корректно отслеживается; не торгуемый предмет получает статус «не торгуется» и не опрашивается.
4. Сборщик **никогда** не опрашивает предметы вне `watchlist` (проверка логами и тестом).
5. Для отслеживаемых предметов в сигналах и тестах используется комиссия 5%; безубыточность ≈ +5,26% отражена в тестах и в пояснениях сигналов.
6. Анонимный клиент не может читать сигналы/список/историю и не может писать; владелец может (проверка RLS тестами).
7. `digest.json` содержит только отслеживаемые предметы и доступен только после входа.
8. Список отслеживания можно экспортировать и импортировать.

## 11. Что сообщить пользователю по завершении Фазы 1

- Расчётный размер БД для 30 и для 100 отслеживаемых предметов.
- Подтверждены ли `listing_fee` и база начисления комиссии; если нет — на что агент это допускает.
